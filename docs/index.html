01Introduction & first steps

What DIG is, the five words you need, and your first pipeline in five minutes.

DIG is a self-hosted, plugin-first data-preparation tool. You work the way you'd work in a spreadsheet — click a column, filter it, cast it, group it — but behind every move DIG records a step in a real, portable pipeline. Nothing you do is a dead end: undo anything, replay it on new data, share it as a small JSON file, or schedule it to run every morning.

The one idea that makes DIG different

Most tools force a choice: a snappy in-browser toy that can't handle real data, or a heavyweight server tool with no live feedback. DIG refuses the trade-off with a dual-engine architecture. The exact same pipeline runs two ways:

⚡

In your browser

DuckDB-WASM previews every edit on a sample of your data, sub-second, as you type — no round-trip to a server.

🗄️

On the backend

When you press Run, DuckDB (or Polars) executes the same steps over the full dataset and writes results to disk.

Why it mattersDIG ships byte-for-byte parity tests for every step, so the preview you trust in the browser is the result you get on the backend. A pipeline describes what to do, never where to run it.

Privacy posture: your data stays put

DIG is local-first by design. Datasets live in your own data directory; the backend runs on 127.0.0.1; no telemetry, no upload, no account. The optional AI assistant is off by default and, when enabled, talks only to the provider you point it at (including a fully-local Ollama). DIG is licensed AGPL-3.0-or-later.

Your first five minutes

  1. Install, start, open.

    Three commands from the project root: ./install.sh (one-time setup), ./start.sh (start the server), ./stop.sh (stop it when you're done). With the server running, open http://localhost:3100. See §2 for the detail.

  2. Try with sample data.

    On the Home screen, click 🌱 Try with sample data — DIG imports a demo dataset and drops you into the editor with a starter pipeline.

  3. Shape a column.

    Click any column header → choose an action (filter, sort, cast, group…). Watch the live grid update instantly. That action just became a step in the bottom strip.

  4. Press Run.

    Hit ▶ Run to execute the whole pipeline on the backend over the full dataset. The result is written as Parquet to your data directory.

  5. Keep going.

    Everything else in this manual builds on that loop: Ingest → Shape → Run. The six worked examples (§9) take it end-to-end.

The one-command install

From the project root, run the guided installer. It's idempotent — re-run it any time to verify or repair; already-installed tools are reported as ✓ and skipped.

# clone, then from the project root:
./install.sh

The installer walks four phases, printing what it's about to do and asking once before changing anything:

  1. System tools.

    Homebrew on macOS, Python 3.11+, and pnpm — installed only if missing.

  2. Optional JDBC extras.

    cmake + a Temurin JDK + Apache Ant + jpype1, for the JDBC connector and the export_to_jdbc step. Skippable.

  3. Project dependencies.

    The backend .venv and the frontend node_modules.

  4. Start DIG.

    Brings the API + web UI up in the background and prints the URLs.

Open it

When the installer finishes, DIG is already running. Open the web UI and click 🌱 Try with sample data:

Web UI http://localhost:3100 API http://localhost:8190 HTTPS (opt-in) :3443 / :8443
HTTP and HTTPSDIG serves plain HTTP on 3100/8190 out of the box. A self-signed TLS path on 3443/8443 is available for LAN access — see Settings → Server & TLS (§4).

Day-to-day commands

Power users and CI can drive DIG with discrete commands instead of the installer:

make setup     # one-time: backend venv + pnpm install
make start     # detached; writes a PID file, prints URLs
make status    # is it up? where?
make stop      # graceful TERM, escalates to KILL after 5s
make dev       # foreground (Ctrl-C to stop)
make restart   # stop + start
./start.sh                 # start in the background
./scripts/dig-status.sh    # status + URLs
./stop.sh                  # stop
./upgrade.sh               # pull + migrate to a newer version
./scripts/dig-start.sh --api-port 9000 --web-port 4000   # one shot
./scripts/dig-start.sh --api-port 9000 --save            # persist to config
./scripts/dig_config.py show                             # effective config

Native launchers (optional)

Both wrappers run the same shell scripts and the same ~/.config/dig/config.json:

make mac-app        # builds DataInsightGrove.app (macOS)
./linux/install.sh   # adds the .desktop entry (Linux)

Upgrading

Run ./upgrade.sh to fetch a newer version; DIG auto-migrates its config and on-disk state on the next boot. See Settings for where that state lives.

If a step failsRe-run ./install.sh — it diagnoses and repairs rather than starting over. For a clean slate, ./install.sh --rebuild nukes .venv + node_modules first.

The pipeline editor layout

When you open a pipeline for editing, the screen splits into three regions: data-first (top), steps (bottom), and settings (right).

Top region: Live Grid

The grid shows the output of whichever step you've selected in the strip. It updates automatically as you edit — no separate Preview button. Click a column name to open the Column Profile drawer: see the type, nulls, cardinality, histogram (for numerics), top-N values, and quick-filter buttons. Right-click a column header (or click the ⋯ menu) to sort, filter, cast, drop, or derive from that column — actions are inserted as new steps directly in the pipeline.

Interactive: click column name → Profile drawer Interactive: ⌘+click cell → Filter to value Interactive: ⌘+Alt+click → Exclude value

Bottom region: Strip and Graph views

The pipeline's steps are arranged in two complementary views, toggled via a button in the editor header:

Strip view is linear and sequential. Every step is a numbered card showing the category emoji, label, status badge (✅ success, ❌ error, ⏳ running, ⏸ paused), row count, and time since last run. It's the quickest way to scan the pipeline flow and click a step to edit it.

The Strip has a fixed 58px height and never scrolls off-screen — the data grid above scrolls internally, keeping the steps always visible.

Graph view is the true DAG: nodes (datasets, steps, outputs) with edges showing data flow. Useful for joins, unions, and complex multi-input pipelines. You can drag nodes to rearrange them; positions persist in the document. A resize handle above the graph (visible on hover) lets you adjust its height (120–700px). The graph includes a mini-map (top-right corner) and a zoom/pan toolbar.

Both views show the same pipeline — switching between them doesn't change the document, just how you see it.

Browser preview — DuckDB-WASM sample size

The live grid recomputes as you edit, powered by DuckDB running in your browser. Sample size controls how many rows the in-browser engine scans — the options are 10,000 | 50,000 | 100,000 | 500,000 | 1,000,000.

Lower samples (10K–50K) keep the grid responsive on slower machines and dense datasets. Higher samples (500K–1M) show more representative data but trade latency. For development, 100K is a practical middle ground. Toggle Auto-recompute on every edit off on very slow machines to only run the grid when you explicitly click.

Server & TLS — ports and HTTPS setup

DIG serves both HTTP and HTTPS automatically. The backend runs on HTTP ports (API: 8190, Web: 3100) and an optional TLS proxy terminates HTTPS on separate ports (API: 8443, Web: 3443), forwarding decrypted traffic back to the HTTP ports.

Boot-time settings (require restart):

  • Log directory — where rotating log streams live. Defaults to /var/log/DIG (Unix); falls back to ~/Library/Logs/DIG (macOS) or ~/.local/state/DIG/logs (Linux) if sudo is declined.
  • Log file size limit (bytes) — per-stream rotation threshold. Default 10 MB; logs roll from .log → .log.1 → .log.2, etc.
  • Log rotations kept — how many rolled files to retain per stream. Default 5, meaning up to 50 MB history per stream.
  • HTTPS enabled — when on (default), the TLS proxy runs alongside HTTP. When off, only http:// is available.
  • Auto-install cert in system trust store — on first start, prompts for sudo to install the self-signed cert into the system keychain. Happens exactly once; re-trigger with ./scripts/dig_tls.py trust.
  • API HTTPS port and Web HTTPS port — ports the TLS proxy listens on. Defaults 8443 (API) and 3443 (Web).

AI assistant — local and cloud providers

Default: disabled. When enabled, DIG offers natural-language help for pipeline editing: explain a column, fix an expression, or generate a connector.

Local (recommended): Run Ollama on your machine. No API key, data stays private. Setup:

  1. Install and start Ollama.

    macOS: brew install ollama then ollama serve. Linux / Windows: see ollama.com/download.

  2. Pull a model.

    Example: ollama pull gemma4:e4b (~7 GB, recommended). Or ollama pull gemma3:4b (~3 GB, edge-optimized).

  3. Configure DIG.

    Set AI provider = local, Endpoint URL = http://localhost:11434/v1 (Ollama's default), Model = your chosen model, then toggle Enable AI assistant on.

  4. Test connection.

    Click the Test connection button; a green check means the LLM is reachable.

Cloud / OpenAI-compatible: For Anthropic, OpenAI, Groq, or OpenRouter, set AI provider = openai_compat, paste your API key into API key, and point Endpoint URL at the provider:

  • Anthropic: https://api.anthropic.com/v1 (model: claude-haiku-4-5)
  • OpenAI: https://api.openai.com/v1 (model: gpt-4o-mini)
  • Groq: https://api.groq.com/openai/v1 (model: llama-3.1-70b-versatile)

Data access control: By default, Allow non-local AI providers is OFF, so only 127.0.0.1 (localhost) endpoints are reachable — your pipeline data never leaves the box. Turn the toggle ON to permit cloud APIs and LAN hosts (e.g., Ollama on another machine). Link-local and cloud-metadata addresses stay blocked regardless; only set DIG_AI_ALLOW_PRIVATE=1 if you have an internal trusted model host.

Optional tuning: Max output tokens (default 4096), Temperature (default 0.0 for deterministic code generation), and Ping interval (in seconds, to keep local models warm).

JDBC drivers — managed library vs. path reference

Register a driver JAR and class once, then pipelines using the jdbc connector or export_to_jdbc step pick from the list instead of typing paths. Two modes:

Upload (recommended): Copy the JAR into DIG's managed library (data/jdbc-drivers/). It travels with your DIG state during backup or migration, and you never expose a filesystem path.

Reference (advanced): Point at a JAR already on the server (e.g., a shared network mount). The path is not copied, so the operator owns keeping it available.

For each driver, record:

  • Display name — human label (e.g., "Oracle 19c")
  • Driver class — JDBC class name (e.g., oracle.jdbc.OracleDriver)
  • Driver JAR — upload a .jar or reference a filesystem path
  • URL template (optional) — example JDBC URL the UI pre-fills (e.g., jdbc:oracle:thin:@//<host>:1521/<service>)
  • Notes (optional) — compatibility info

After adding a driver, use Test connection to verify the JAR loads and (optionally) try a real connection with a test URL and credentials. The test URL and creds are never saved — they're ad-hoc and only used to validate the driver works before it's used in a pipeline.

Step Packs — install plugin bundles

DIG's core steps can be extended with .dpack bundles — packages of custom steps, connectors, or templates. Install a pack to add new affordances to the pipeline editor. Uninstall to clean up unused plugins. Each pack declares its dependencies and versions; DIG auto-installs Python requirements by default (set DIG_PACK_AUTO_INSTALL_DEPS=0 to manage them manually).

Tip Use the search field at the top of the sidebar to fuzzy-filter settings by name or description — instantly jump to "JDBC" or "Log level" without scrolling.
Config file reference Boot-time settings (Server & TLS) are read from ~/.config/dig/config.json by scripts/dig-start.sh before the API starts. Runtime settings (AI, Storage, Performance, etc.) live in DIG's SQLite metadata database. Environment variables (e.g., DIG_AUTH_TOKEN, DIG_API_PORT) override both. See docs/CONFIG.md for the full reference.

DIG handles both direct file uploads and references to files without copying them — your data stays yours.

Input data is sacred. Reference a file on disk, a remote URL, or a database query without copying. DIG reads it fresh on every pipeline run.

Automatic type detection and profiling

When you ingest a dataset, DIG profiles every column and detects its data type. The system recognizes 29 data typesstring, integer, double, boolean, date, datetime) and 23 meta-types that describe what values mean — coordinates (geographic, polar, Cartesian), currency with exact decimal arithmetic, UUID, email, URL, IP address, color, phone number, timezone, scientific notation, vectors, JSON, and more.

The profile shows per-column statistics (null fraction, distinct count, min/max, top values, distribution) and drives the auto-detection of meta-types. A column that looks like geographic coordinates, email addresses, or currency is labeled accordingly — even when stored as plain strings or numbers. You can always override the auto-detection from the column menu (⋯ → 🔄 Cast to…).

Sampling for live preview

The pipeline editor renders a live preview on a sample of your data — not the full dataset. This keeps the editor snappy. Pick how that sample is drawn from the toolbar's 🧪 sampling button:

  • 🔝 Head — first N rows (default, fastest, same as SQL LIMIT).
  • 🔚 Tail — last N rows (for time-series "most recent" inspection).
  • 🎲 Random — uniform random sample with optional reproducibility seed (best for representative previews).
  • 📐 Systematic — every Nth row, preserves ordering trends across the dataset.

The sampling setting travels with the pipeline (saved in the document) so each workflow can use a different method. Full-data backend runs always use 100% of your data, regardless of preview sampling.

Add a dataset

  1. Open the Datasets page.

    Click Datasets in the sidebar (or use keyboard shortcut g d) to see all imported data.

  2. Drag a file or click to upload.

    Drop a file onto the page, or click the upload button. Supported formats: CSV, Excel, JSON, Parquet, Feather, SQLite, and scientific binaries (NumPy, HDF5, MATLAB, NetCDF, FITS if the [science] extra is installed).

  3. Or add a reference to external data.

    Click Add dataset and choose a connector — HTTPS URL, REST API with auth, Postgres, MySQL, JDBC, Snowflake, BigQuery, Google Sheets, or dbt models. Enter the connection details and DIG fetches rows on demand, no copy stored locally.

06Data manipulation

Shape, clean, derive, combine, aggregate, analyze, and validate with 62 built-in steps across 11 categories. Undo any change with ⌘Z.

The mental model

Every column transformation — selecting, casting, filtering, computing, combining — becomes a step. Steps chain left-to-right in the editor's strip; data flows through them. Each step is undoable: press ⌘Z to rewind any action back through the entire run history. This means you can experiment fearlessly — add a step to explore, then undo if it doesn't lead anywhere.

TipThink of steps as column-level operations. To select columns, use Select columns. To filter rows, use Filter rows. To add a computed column, use Derive column or Add runtime column. To reshape, pack, unpack, or transpose, reach for the shape family.

Joins: Combining two datasets by matching keys

A join matches rows from two inputs — a dataset, an upstream step, or both — using one or more key columns. The Join step's panel is hand-built to surface the row-count consequences before you commit.

Join type (cardinality)

Six join types control which rows survive:

  • Inner — matching rows only.
  • Left — keep all rows from the left input; right rows that don't match become NULLs.
  • Right — keep all rows from the right input; left rows that don't match become NULLs.
  • Full — keep both sides' rows (outer join). Unmatched pairs get NULLs.
  • Anti-left — rows on the left WITHOUT a matching right row (useful for 'find unmatched').
  • Anti-right — mirror of anti-left.

Key pairs

For each key pair [left column] [op] [right column], the panel shows:

  • Column — the column name from each side.
  • Op — = (equality, most common), or < / <= / > / >= for range joins.
  • Match-quality bar — green (high overlap) to rose (low overlap) on the sample. Click to see the overlap percentage inline.
  • Remove (✕) — delete the key pair.

Equality keys (op = =) collapse in the output: the right side is dropped because its values are always identical to the left. Range-key pairs carry both sides.

Result columns

At the bottom, a grid shows every output column with provenance chips (L for left, R for right, C for coalesced). You can exclude columns (checkbox) or rename them inline. Provenance identifiers are stable — your renames and exclusions survive changes to the join kind, suffix rules, or collision strategy.

Any pipeline can be published as a step and installed in other pipelines. The published pipeline becomes a single node in the consumer's strip; at compile time, DIG inlines it into the flat DAG.

Publishing

In the editor toolbar, click 🪆 Publish. Fill in:

Pinned versions

When you install a sub-pipeline step, the parent records a specific source version (pinnedEtag). The parent's behaviour is locked until you explicitly click ⬆ Upgrade. Three pin states:

  • Up to date with source. — pinned etag matches the source's live version.
  • n versions behind source (v). — source has advanced; click ⬆ to bump.
  • Source pipeline unavailable. — the source was deleted; remove this node or republish a replacement.

Exposed parameters

Most reusable sub-pipelines need a few knobs. Open any node in your source pipeline → params panel → each param's row has a 🪆 expose pill:

  • Default (grey) — param is hidden from consumers.
  • Click once (violet) — param is exposed with a consumer-facing alias. Defaults to the param key.
  • Click again — unexpose; the alias is dropped.

Consumers see the exposed aliases as regular params on the step; their values flow into the inner nodes at inline-expansion time.

Cycle detection

DIG automatically detects and blocks circular references. When you save or start a run, the system checks whether any sub-pipeline references create a loop (direct or transitive). If so, you get a clear error with the offending chain. The picker also blocks self-cycles immediately with a 7-second toast.

Hints: One-click rule-based composites

Hints are AI-suggested step sequences that you can apply in one click. They recognize common patterns — like raw latitude/longitude columns — and bundle the right steps together. For example, the (lat, lon) → pack & cast hint detects a pair of lat/lon columns and suggests packing them into a struct, then casting to a geographic type so downstream steps can use them as a single geographic column.

When DIG detects a pattern matching a known hint in your current dataset, a suggestion appears in the sidebar. Click Apply to insert the composite, or Apply as branch to try it on a fork of your current pipeline without modifying your working version.

    The popover shows current vs previous distribution + a KL divergence number. Switch to Engineer mode (⌘⇧E) to see the raw KL value and unlock the per-column "compare to" picker for comparing against any historical run.

  15. Click Review (🔍) to run AI review in Engineer mode.

    Engineer mode shows confidence percentages and SQL-level diffs. Typical findings surface forecast variance growth, SQL optimization hints, and anomaly checks on adjacent columns. Apply suggestions to see the diff drawer; accept to update the pipeline.

Example 5: E-commerce channel revenue & AI-driven cleanup

Goal: Clean a 5,000+ order dataset with quality issues, compute revenue by channel × category × week, surface data quality problems with the AI Reviewer, and export a clean CSV.

Dataset orders-demo.csv (5,023 rows) Key steps cast_type · filter_rows · expectations · group_aggregate · sort_rows Output CSV export Best feature AI Pipeline Review

    Datasets → Import and drop orders-demo.csv. The live profile shows the header histograms: channel has 5 categorical bars (organic dominant), revenue and fulfillment_hrs have long tails, qty is skewed toward 1.

    Name it Channel revenue weekly.

  3. Add cast_type to convert order_ts to datetime.

    CSV ingest reads timestamps as strings; cast is required for the date truncation in the next step.

Example 6: Factory sensor analysis & defect prediction

Goal: Derive leading-indicator vibration & temperature features from 43K rows of factory telemetry, detect defect-prone shifts, and ship a multi-panel chart for reliability engineering triage.

Dataset manufacturing-demo.csv (43K rows) Key steps cast_type, filter_rows, rolling, window_aggregate, group_aggregate Output PNG chart + CSV export Best feature Vibration std 15m rolling with per-machine p95 flag
  1. Import manufacturing-demo.csv.

    Datasets → Import. Profiles show 6 lines, 15 machines, ~0.5% defect events, sporadic sensor blackouts (NULLs), and ~20 unphysical temperature spikes >200°C.

  2. Create "Factory defect signals" pipeline.

    New pipeline to isolate one production line for clarity.

  3. Add cast_type step.

    Map column ts → datetime. Strict off so malformed timestamps become NULL rather than failing the run.

  4. Add filter_rows step.

    Predicate: line_id = 'LINE-D'. Scopes to 7K rows (LINE-D has the degrading machine M-D1). Filters before rolling computation avoid wasting ~85% of windowing work.

  5. Add expectations quality gate.

    Three rules: temperature_c BETWEEN 0 AND 200 (warning), vibration_mm_s >= 0 (error), machine_id IS NOT NULL (error). Warning severity surfaces faulty-sensor rows without failing the run.

  6. Add window_aggregate for defect lookback.

    Function max, source column is_defect_event, partition by machine_id, order by ts ascending, alias defect_5min_lookback. Creates a leading-window feature showing defect 1 tick ahead (5 minutes at your granularity).

  7. Add rolling step for vibration & temperature.

    Time column ts. Two windows: vibration_mm_s std 15m (alias vibration_std_15m), temperature_c mean 15m (alias temperature_mean_15m). Min periods 2. Sparklines on vibration_std_15m show clear spikes where defect pre-signals appear.

  8. Add derive_column for per-machine vibration p95 flag.

    Name vibration_above_p95. Expression: vibration_mm_s > QUANTILE_CONT(vibration_mm_s, 0.95) OVER (PARTITION BY machine_id). Per-machine normalization beats global thresholds — different machines have different baselines.

  9. Add group_aggregate for fleet roll-up.

    By machine_id, shift. Aggregations: ts count (n_ticks), temperature_c mean (temperature_mean), temperature_c max (temperature_max), vibration_mm_s mean (vibration_mean), vibration_mm_s std (vibration_std), is_defect_event sum (defects).

  10. Add sort_rows step.

    Sort by defects descending. Worst-shift-first is the correct triage order for the reliability engineer.

  11. Add export_to_image step.

    Chart kind line, X column ts, Y columns temperature_c, vibration_mm_s, defect_count_running, title "LINE-D telemetry — temperature + vibration with defect overlay".

  12. Add export_to_file step.

    Format csv, path factory-defect-signals.csv. Add an output pointing at the CSV step.

  13. Run on backend.

    Completes in 3-4 seconds on backend DuckDB/Polars. Artifacts panel shows PNG card + CSV card. Click vibration_std_15m column header to open the rich profile drawer — histogram shows bimodal distribution with baseline vibration cluster and long thin tail of defect pre-spikes.

Tip The AI Pipeline Reviewer earns its keep on telemetry: it flags leading-window information leakage (your defect_5min_lookback column), rolling computations placed after filters (wasting work), and per-machine normalization gaps. Click 🔍 Review in the toolbar to see severity-ranked findings — these are the kinds of nitpicks a senior reliability engineer would surface in PR review.

10Addendum — Packs & their features

What a pack is, the 6 bundled packs, and how to author your own.

What is a Pack?

A Pack is a distribution unit that bundles one or more steps (and optionally connectors). Instead of adding individual steps scattered across your filesystem, you install or remove packs as whole archives (`.dpack` files) via Settings → Step Packs. Steps that come from a pack get a faint violet row tint and a 📦 source tag in the step picker, so you always know which extension a step came from.

How Packs are Structured

Every pack follows the same folder layout:

my_pack/
├── pack.json          ← manifest: id, version, steps, dependencies, resources
├── README.md          ← narrative description
├── LICENSES.md        ← license + attribution roll-up
├── data.zip           ← bundled reference data (optional)
├── steps/
│   └── my_step/
│       ├── manifest.json
│       └── step.py
└── connectors/        ← optional

The pack's pack.json declares which steps it contains, any Python dependencies it needs, and (if present) reference data files for lookup operations. The framework discovers and registers your pack on startup — no boilerplate registration needed.

In a bit more detail

📄

Dataset

Your imported data — CSV, TSV, Excel, JSON, Parquet, Feather, generic delimited text, and scientific binary formats (NumPy, HDF5, MATLAB, NetCDF, FITS). DIG profiles every column on import so you know what you're working with. Datasets live in your local data directory — DIG never uploads them.

🔌

Connector

Each file format and external system (REST, JDBC, Postgres, MySQL, SQLite…) is a small connector plugin: one Python file + one JSON manifest under backend/connectors/. Drop in your own and DIG picks it up on next start.

🪢

Pipeline

A directed graph of steps that consumes datasets and produces output. Pipelines are portable — stored as a small .dig.json document you can commit to git, share, or replay against a different dataset of the same shape. A pipeline says what to do, never where to run it.

🧩

Step

A single transformation: keep some rows, change a column's type, group and aggregate, join two inputs, derive a column from an expression, write a file, train a model, render a chart. DIG ships 62 built-in steps plus packs — and you can drop in your own.

📊

Profile

On ingest, DIG runs every column through a stats pass: physical type, null fraction, distinct count, min/max, top values, distribution. The profile feeds the header tooltip, smart cast picks, and the Hints panel — and auto-detects meta-types (emails, currencies, coordinates, vectors…).

🔬

Sample

The editor recomputes a live preview on every change. To stay snappy, that preview runs on a sample (default 100,000 rows) in DuckDB-WASM in your browser. The full dataset is only touched when you Run on the backend. The status strip always shows the sample size in use.

🧠

Hint

The Hints panel shows deterministic, rule-based observations from the column profile — "this column is 30% null — drop nulls?", "these two columns look like (lat, lon) — pack and cast to geographic". Not predictions, not ranked AI cards — a calm "by the way…" you can apply with one click.

▶️

Run

One execution of the whole pipeline on the backend over the full dataset. Runs happen as background jobs (navigate away and come back), produce Parquet by default, and surface progress + logs. Past runs are listed under Run history.

📤

Output

What a pipeline writes when run. By default Parquet to your local data directory; you can also configure other sinks (another file format, a database, a webhook, a rendered chart). Outputs are first-class, versioned with the rest of the steps.

⏰

Schedule

A pipeline can run automatically on a standard cron expression (0 6 * * *). The Schedules page lets you add, list, pause, or trigger a scheduled pipeline; history shows every triggered run and its outcome.

🔍

Lineage

Optional per-row source tracing. Turn on 🔍 lineage in the editor and the run records which input row(s) each output row came from — then click 🔍 on any output row to jump back to the source. Adds ~10–30% run time; off by default.

🪆

Module

A pipeline you've packaged for reuse. Drop a module into another pipeline as a single node and DIG runs it inline like any other step — a small library of reusable patterns without copy-pasting steps between pipelines.
